### 새로 배운 내용
#### 주제 1: 공유 자원, 임계 영역과 실무적 관점
- **공유 자원과 임계 영역**: 여러 프로세스/스레드가 동시에 접근하는 한정된 리소스를 공유 자원이라 하며, 이 자원에 접근하여 데이터를 수정하는 코드 블록을 임계 영역이라고 합니다. 단순히 자원을 읽기만 하는 코드는 임계 영역에 해당하지 않을 가능성이 높습니다.
- **백엔드 개발자 관점**: 운영체제 레벨의 락을 직접 다루기보다는 DB 트랜잭션, Redis 분산 락, 메시지 큐(Consumer Lock), 캐시 갱신(CAS, TTL), 커넥션 풀 등 이미 동기화 개념이 추상화되어 녹아있는 기술들을 통해 동시성을 제어합니다.
- **인프라 엔지니어 관점**: 코드보다는 실제 공유 리소스의 경합에 집중합니다. 커널 내부 락, 파일 시스템(MVCC), 네트워크 스택, 컨테이너 런타임의 리소스 충돌 제어, 쿠버네티스 컨트롤러의 상태 갱신 등 시스템 전반의 락 경합과 데드락을 분석합니다.

#### 주제 2: 락(Lock)의 정의와 6단계 동작 프로세스
- **락의 정의**: 하나의 스레드나 프로세스가 자원을 점유했을 때 다른 접근을 배타적으로 제어하여 데이터 무결성 손실과 경합 조건(Race Condition)을 방지하고 원자성을 보장하는 동기화 기법입니다.
- **락의 동작 단계**: 스레드가 자원 접근 전 락을 **① 요청**하고, 비어있다면 **② 획득**한 뒤 **③ 임계 영역을 실행**합니다. 이 동안 다른 스레드는 **④ 대기**하며, 작업이 끝난 스레드가 **⑤ 락을 해제**하면 대기 중이던 다음 스레드가 **⑥ 진입하여 락을 획득**하고 작업합니다.

#### 주제 3: 스핀락(Spinlock)과 낙관적 락(Optimistic Lock)
- **스핀락**: 락이 해제될 때까지 대기 상태로 전환되지 않고 바쁜 대기(Busy-waiting) 상태로 루프를 돌며 반복 확인하는 방식입니다. 컨텍스트 스위칭 오버헤드가 없어 임계 영역이 매우 짧을 때 효과적이지만, 대기가 길어지면 CPU 사용률이 급증하므로 백엔드보다는 주로 OS 레벨에서 쓰입니다.
- **낙관적 락**: 데이터 충돌이 거의 없을 것이라고 '가정'하고 별도의 락 없이 작업을 수행한 뒤, 최종 시점에 충돌 여부(버전 등)를 검사하는 방식입니다. 초기 락 오버헤드가 없어 읽기 중심 시스템이나 분산 환경에서 병렬 처리를 극대화할 수 있지만, 실제 충돌 발생 시 롤백 및 재시도 비용이 크게 발생합니다.

#### 주제 4: 뮤텍스(Mutex)와 조건 변수, 그리고 리드-라이트 락(Read-Write Lock)
- **뮤텍스**: 한 번에 하나의 스레드만 임계 영역에 진입하도록 제한하며, 락을 획득한 스레드가 '소유권'과 '해제 권한'을 독점합니다. 락을 얻지 못한 스레드는 대기 큐(Wait Queue)에서 대기하며, 조건 변수(Condition Variable) 메커니즘을 결합하면 특정 전제 조건이 충족될 때까지 스레드를 대기 상태로 두었다가 신호(`signal()`)를 보내 깨울 수 있습니다.
- **리드-라이트 락**: 읽기(Reader) 작업과 쓰기(Writer) 작업을 분리하여 제어합니다. 데이터 무결성을 위해 쓰기 작업은 독점적으로 처리되지만, 데이터를 읽는 다중 스레드는 동시에 자원에 접근할 수 있어 읽기 중심 캐시나 파일 시스템에서 효율적입니다. 단, Reader가 지속해서 유입될 경우 Writer가 굶주리는 기아 현상이 발생할 수 있어 정책(Reader/Writer 우선 정책) 고려가 필요합니다.

#### 주제 5: 안전한 동시성 제어를 위한 실무 팁
- **범위 최소화와 안전한 해제**: 무조건 락을 많이 건다고 안전해지는 것이 아니며, 오히려 성능 저하, 교착 상태(Deadlock), 기아 상태 등을 유발하므로 임계 영역은 최대한 작게 잡아야 합니다. 또한, 예외 발생 시에도 반드시 락이 해제되도록 `finally` 블록을 활용해야 합니다.
- **락 순서 통일과 분산 환경**: 여러 개의 락이 필요하다면 데드락을 방지하기 위해 항상 일정한 순서(예: 항상 A 락 획득 후 B 락 획득)로 코드를 작성해야 합니다. 또한, 서버가 여러 대인 다중 환경(분산 환경)에서는 로컬 락만으로 동시성을 제어할 수 없으므로 DB Lock이나 Redis 기반의 분산 락, 혹은 데이터베이스의 Unique 제약조건과 트랜잭션을 적극적으로 활용해야 합니다.
