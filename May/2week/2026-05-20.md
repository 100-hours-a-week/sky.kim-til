#### 주제 1: OOP
OOP(Object-Oriented Programming)
- 객체지향 프로그래밍
    - 현실 세계의 객체 개념을 기반으로 데이터를 속성(필드)과 기능(메서드)로 묶어 프로그램을 설계하는 패러다임

- SRP(Single Responsibility Principle) - 단일 책임 원칙
    - 하나의 클래스가 하나의 역할과 하나의 변경 이유만을 가지도록 설계해야 한다는 객체지향 설계 원칙
    - 사용 이유 : 요구사항 변경이 잦은 실무 환경에서도 수정 범위를 최소화하고, 각 계층의 책임을 명확히 유지하기 위해서

- OCP(Open Closed Principle)
    - 소프트웨어의 기능 확장은 열려 있고, 기존 코드의 변경은 닫혀 있어야 한다는 객체지향 설계 원**칙**
    - 사용 이유 : 기존 코드를 수정하지 않고 새로운 기능을 추가할 수 있어, 유지보수성과 안정성이 크게 향상되기 때문에

# JVM (Java Virtual Machine) 핵심 요약

## 1. JVM 정의 및 사용 이유

* **정의:** 자바 바이트코드를 실행하는 가상 머신으로, 자바 프로그램이 운영체제(OS)에 종속되지 않고 동일하게 동작하도록 지원하는 핵심 엔진입니다.
* **사용 이유:** OS 독립적 실행이 가능하며 메모리 관리(Heap, Stack, GC), 예외 처리, 보안, JIT 최적화 등 안정적인 런타임 환경을 제공하기 때문입니다.

---

## 2. 자바 프로그램 실행 흐름

자바는 컴파일 언어와 인터프리터 언어의 장점을 결합한 방식을 취합니다.

```
[개발자] .java 소스 코드 작성 
   ▼
[컴파일러] javac 명령어로 컴파일 ➡️ .class 바이트코드 생성
   ▼
[JVM] 클래스 로더가 메모리에 로드 ➡️ 런타임 데이터 영역 배치 ➡️ 실행 엔진이 실행

```

---

## 3. 클래스 로더 (Class Loader) 단계

필요한 시점에 동적으로 `.class` 파일을 읽어오는 **지연 로딩(Lazy Loading)** 방식을 사용하며, **로딩 ➡️ 링킹 ➡️ 초기화** 과정을 거칩니다.

### 1) Loading (로딩)

외부 저장소에서 `.class` 파일을 읽어 JVM 메서드 영역에 올립니다. 보안과 격리를 위해 3가지 로더로 나뉩니다.

* **Bootstrap Class Loader:** 최상위 로더. 자바 자체의 핵심 정품 라이브러리(`java.lang.*` 등)를 로드합니다.
* **Extension Class Loader:** 부트스트랩의 자식. 확장 자바 클래스들을 로드합니다.
* **Application Class Loader (시스템 클래스 로더):** 개발자가 작성한 애플리케이션의 클래스 파일(`.class`) 및 지정된 Classpath 내 파일들을 로드합니다.

> 💡 **클래스 로더를 3개로 나눈 이유**
> 독립된 공간(네임스페이스) 격리, 부모 위임 체계(안전성 검증), 출신 성분에 따른 차별(런타임 패키지 분리)을 통해 외부 악성 코드가 정품 라이브러리를 흉내 내거나 파괴하는 것을 막기 위함입니다.

### 2) Linking (링킹)

클래스를 실제로 사용하기 전에 올바른지 검증하고 준비하는 단계입니다.

* **Verifying (검증):** 파일이 JVM 명세에 맞게 정확히 작성되었는지 검사 (타입 불일치, 접근 제한 위반 등 체크).
* **Preparing (준비):** `static` 변수를 위한 메모리 공간을 확보하고 기본값(0, null 등)으로 초기화합니다.
* **Resolving (해결):** 심볼릭 레퍼런스(이름 기반 참조)를 실제 메모리 주소인 다이렉트 레퍼런스로 변환하여 검색 시간 단축 및 성능을 향상합니다.

### 3) Initializing (초기화)

* `Preparing` 단계에서 확보한 메모리에 `static` 변수의 실제 코드 정의 값을 대입합니다.

## 4. 런타임 데이터 영역 (Runtime Data Area)

| 영역 (Area) | 설명 | 공유 범위 |
| --- | --- | --- |
| Method Area<br>(메서드 영역) | 클래스 구조, 필드/메서드 메타데이터, 메서드/생성자 바이트코드, **런타임 상수 풀**(공통 참조 데이터 저장소) 등을 저장하며 JVM 시작 시 생성됩니다. | **모든 스레드 공유** |
| Heap Area<br>(힙 영역) | 런타임에 동적으로 생성되는 객체(인스턴스)들이 저장되는 공간입니다. **가비지 컬렉터(GC)**가 자동으로 메모리를 관리합니다. | **모든 스레드 공유** |
| Stack Area<br>(스택 영역) | 메서드 실행 시 필요한 임시 공간으로 기본형 변수, 매개변수 등이 저장됩니다. 메서드 호출 시 스택 프레임이 쌓이고 종료 시 제거되는 LIFO 구조입니다. | **스레드별 독립 생성** |
| PC Register<br>(프로그램 카운터) | 현재 스레드가 실행 중인 JVM 명령어의 주소를 기록하여 실행 흐름을 추적하고 제어합니다. | **스레드별 독립 생성** |
| Native Method Stack<br>(네이티브 메서드 스택) | 자바 외 언어(C, C++, 어셈블리 등)로 작성된 네이티브 코드를 실행하기 위한 별도의 스택 영역으로 **JNI**와 연결됩니다. | **스레드별 독립 생성** |

---

## 5. 실행 엔진 (Execution Engine)

메모리에 로드된 바이트코드를 기계어로 변환하여 실제로 실행하는 장치로, 두 가지 전략을 병행합니다.

* **Interpreter (인터프리터):** 바이트코드를 명령어 단위로 하나씩 읽어서 즉시 실행합니다. 반복 호출 시 매번 새로 해석하므로 속도가 다소 느립니다.
* **JIT Compiler (Just-In-Time 컴파일러):** 인터프리터의 단점을 보완합니다. 자주 실행되는 "중복 코드(Hot Spot)"를 미리 통째로 컴파일해 기계어로 변환해 두고, 이후에는 해석 없이 변환된 기계어를 바로 실행하여 성능을 극대화합니다.
