### 주제 1: 웹의 통신 특성: Stateful, Stateless, Connectionless

#### Stateful vs Stateless

* **Stateful (상태 유지):** 서버가 클라이언트의 **이전 상태를 기억**하고 있는 방식입니다.
* **Stateless (무상태):** 서버가 클라이언트의 **이전 상태를 기억하지 않는** 방식입니다.
* **사용 이유:** 이전 상태를 찾아 검증하는 시간이 들지 않아 **처리 속도가 빠르고**, 여러 서버가 독립적으로 동시에 요청을 처리(수평 확장)하기 용이합니다.

#### Connectionless (비연결성)

* **정의:** 클라이언트가 서버에 요청을 보내고 서버가 응답을 마치면 **그 즉시 연결을 끊는** 특성입니다.
* **연결을 끊는 이유:** 연결을 지속하려면 서버 메모리에 클라이언트 정보를 계속 저장해야 하므로, 사용자가 늘어날수록 서버 자원(Resource)이 고갈됩니다.
* **사용 이유:** 서버와 클라이언트가 지속적인 연결을 유지하지 않기 때문에, 한정된 자원으로 **동시에 훨씬 많은 사용자 요청을 처리**할 수 있습니다.

### 주제 2: 인증(Authentication)과 인가(Authorization)

| 구분 | 인증 (Authentication) | 인가 (Authorization) |
| --- | --- | --- |
| **개념** | **내가 누구인지 신원을 식별**하는 행위 | 접근 권한을 **검증하고 허가**하는 행위 |
| **목적** | 신뢰할 수 있는 사용자(요청)인지 확인하여 보안 강화 | 사용자별 특정 자원/기능에 대한 접근 통제 |
| **예시** | ID/PW 로그인, 인증서 제출, 토큰 검증 | 일반 회원 vs 관리자 메뉴 접근 권한 차등 부여 |

### 인증/인가의 3가지 주요 방식

1. **HTTP 요청마다 ID/PW 전송:** 매번 신원을 보내는 가장 단순한 방식 (보안에 매우 취약)
2. **세션(Session) 방식:** 서버에 유저 정보를 두고 고유 ID로 식별하는 방식
3. **JWT(JSON Web Token) 방식:** 토큰 자체에 유저 정보를 담아 암호화하는 무상태(Stateless) 방식

### 주제 3: 쿠키(Cookie)와 세션(Session)

> **한 줄 요약**
> * **쿠키:** "사용자의 컴퓨터(브라우저)에 설치되는 작은 기록 정보 파일"
> * **세션:** "두 컴퓨터(클라이언트-서버)가 연결되어 인지하는 기간 또는 상태"

### 쿠키 (Cookie)

* **사용 이유:** HTTP의 Stateless, Connectionless 특성 때문에 과거 방문 기록을 알 수 없으므로, 쿠키를 통해 최소한의 정보를 브라우저에 기록하여 **개인화된 맞춤형 서비스**를 제공합니다. (예: '오늘 하루 보지 않기', '아이디 저장')
* **보안 유의점:** 서버가 클라이언트에게 전달하여 브라우저(사용자 PC)에 직접 저장되므로, 탈취나 변조 위험이 있습니다. 따라서 **공개되어도 무방한 정보만 저장**해야 합니다.

### 세션 (Session)

* **사용 이유:** 중요한 정보를 서버 측에서 안전하게 관리하여 보안을 강화하고, 사용자별 맞춤 정보를 제공하기 위함입니다.
* **동작 방식:** 서버에서 유저별 고유 식별자인 **세션 ID**를 생성해 정보를 저장하고, 브라우저는 이 세션 ID를 **쿠키에 담아** 서버와 통신할 때마다 제출합니다.
* **세션 저장 방식 3가지:**
1. **In-Memory:** 서버 메모리(변수 등)에 직접 저장하는 방식 (속도가 빠르지만 서버 재시작 시 휘발)
2. **File Storage:** Express 등의 서버 코드에서 텍스트 파일 형태로 저장하는 방식
3. **Database:** 관계형 DB나 NoSQL, Redis 등의 데이터베이스 컬럼/Key에 세션 정보를 저장하는 방식

### 주제 4: 프레임워크(Framework)와 라이브러리(Library)

> **제어 흐름의 주체(Inversion of Control)에 따른 차이**
> * **프레임워크:** 개발을 위한 구조와 규칙을 제공하여 개발 과정을 단순화하는 도구 (**틀이 나를 통제**)
> * **라이브러리:** 개발자가 필요한 기능을 직접 호출해서 사용하는 코드의 집합 (**내가 틀을 통제**)

* **프레임워크 사용 이유:** 정해진 규칙 안에서 작업하므로 더 쉽고 빠르며, 팀원 간 코드의 **일관성**을 유지하고 안정적으로 개발하기 위함입니다.
* **라이브러리 사용 이유:** 검증된 소프트웨어 부품(비휘발성 자원의 모임)을 재사용함으로써 개발 속도를 높이고 **전문성** 있는 기능을 쉽게 구현하기 위함입니다.

### 주제 5: API (Application Programming Interface)

* **정의:** 응용 프로그램 인터페이스. 운영체제와 응용 프로그램, 혹은 서로 다른 시스템/객체 사이의 경계에서 **상호 소통하기 위해 만들어진 물리적/소프트웨어적 접점**입니다.
* **사용 이유:** 서로 다른 시스템이나 애플리케이션 간에 데이터를 표준화된 방식으로 교환하고 기능을 안전하게 공유하기 위함입니다.

### 주제 6: 대용량 데이터 처리: 페이징(Paging)

### 페이징 정의 및 필요성

* **정의:** 한정된 용량 내에서 데이터를 한 번에 처리하지 않고, 적당한 크기(페이지 단위)로 나누어 처리하는 기법입니다. (예: 웹 사이트에서 다음 콘텐츠를 불러오는 '인피니트 스크롤링'도 페이징의 일종)
* **사용 이유:** 수천만 건의 데이터를 한 번에 로딩하면 서버와 클라이언트 모두에 극심한 과부하가 걸리고 로딩 시간이 길어집니다. 볼 만큼만 조금씩 나누어 제공하여 **자원 낭비를 막고 부하를 줄입니다.**

### 페이징 방식 종류 비교

| 종류 | 작동 방식 | 장점 | 단점 |
| --- | --- | --- | --- |
| Offset-based<br>(오프셋 기반) | `limit`(가져올 양)과 `offset`(건너뛸 양)을 이용해 페이지 번호 단위로 조회 | 구현이 직관적이고 쉬움.<br>원하는 페이지 번호로 직접 이동이 편리함. | 뒤로 갈수록 DB가 읽어야 할 양이 늘어나 **성능이 저하**됨.<br><br>조회 중 데이터 추가/삭제 시 **중복이나 누락 발생**. |
| Page-based<br>(페이지 기반) | 오프셋 개념을 클라이언트가 이해하기 쉬운 '페이지 번호'로 표현한 방식 | Offset 기반과 유사함. | Offset 기반과 동일한 단점(성능 저하 및 데이터 유실 가능성)을 공유함. |
| Key-based<br>(키 기반) | 특정 페이지가 아닌, 조건(예: `ID > 100`)을 기준으로 그 다음 데이터부터 가져옴 | 인덱스를 타고 직접 접근하므로 데이터가 많아져도 **성능이 저하되지 않음(최적화)**. | 페이지 번호가 없으므로 특정 임의 페이지로의 **점프 이동이 불가능**함. |
| Cursor-based<br>(커서 기반) | 마지막으로 응답한 데이터의 식별자(커서)를 기준으로 다음 데이터를 보여주는 방식 | 실시간 데이터 변동에도 **중복/누락이 없음**. | 특정 페이지 이동이 불가능하며, **순차 이동만 가능**함. 식별자 노출 방지를 위해 **커서 직렬화(인코딩/암호화)**가 필요함. |
| Token-based<br>(토큰 기반) | 마지막 항목의 고유 식별자를 서버가 기억(토큰화)하여 다음 요청 시 활용 | 데이터 **누락 및 중복이 없음**. | 특정 페이지로 바로 이동할 수 없으며, **순차적인 다음 페이지 이동만 지원**함. |
