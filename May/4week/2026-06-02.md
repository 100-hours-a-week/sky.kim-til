### 새로 배운 내용
#### 주제 1: JPA 값 타입과 임베디드 타입
- **기본값 타입**: 단일 값으로만 의미를 가지는 데이터(int, String 등)를 엔티티 필드에 직접 정의하는 방식으로, 식별자가 필요 없는 단순한 값을 관리할 때 사용합니다.
- **임베디드 타입**: 두 개 이상의 값을 하나의 객체로 묶어(`@Embeddable`, `@Embedded`) 재사용하는 값 타입으로, DB 테이블에는 별도 테이블 없이 기본 필드 컬럼으로 나란히 생성됩니다.
- **컬렉션 값 타입**: 엔티티와 직접 연관되지 않는 여러 개의 단순 값(태그 목록, 주소 이력 등)을 별도 테이블에 분리 저장하면서도, 부모 객체와 일괄 관리할 수 있도록 리스트나 세트 형태로 저장하는 방식입니다.

#### 주제 2: JPQL (Java Persistence Query Language)
- **개념 및 특징**: 엔티티 객체를 대상으로 데이터를 조회·조작하는 객체지향 쿼리 언어로, DB에 독립적이고 유지보수하기 쉬운 쿼리 작성을 가능하게 합니다.
- **경로 표현식과 조인**: 점(`.`) 연산자를 통해 객체 관계를 탐색하며, 연관 필드 탐색 시 JPA가 자동으로 SQL 조인을 생성하는 **묵시적 조인**이 발생합니다. 하지만 실무에서는 성능 최적화와 쿼리 명확성을 위해 `join` 키워드를 직접 선언하는 **명시적 조인**을 우선적으로 사용합니다.
- **Fetch Join과 N+1 문제**: 지연 로딩(`LAZY`) 전략으로 인해 연관 데이터를 접근할 때마다 추가 쿼리가 발생하는 **N+1 문제**를 해결하기 위해, `join fetch` 구문을 통해 한 번의 쿼리로 연관 엔티티를 즉시 로딩(`EAGER`)하여 성능을 최적화합니다.
- **페이징(Paging)**: 대용량 데이터의 조회 부담을 줄이기 위해 `setFirstResult(offset)`와 `setMaxResults(limit)`를 지정하여 DB 방언에 맞는 페이징 SQL을 실행합니다.

#### 주제 3: Spring Data JPA
- **Repository 계층**: `JpaRepository` 인터페이스를 상속받는 것만으로도 반복적인 CRUD 메서드와 페이징, 정렬 기능을 자동화하여 개발 생산성을 높여줍니다.
- **쿼리 메서드(Query Method)**: `findByEmail`이나 `existsByEmail`처럼 메서드 이름만으로 JPQL 쿼리를 자동 생성해 주는 기능으로, 가독성과 일관성을 보장합니다.
- **@Query 및 @EntityGraph**: 메서드 이름으로 표현하기 어려운 복잡한 쿼리는 `@Query`로 직접 작성하며, `@EntityGraph`를 사용하면 JPQL 수정 없이 애노테이션 선언만으로 연관 엔티티의 Fetch Join 전략을 덧입힐 수 있습니다.
- **Auditing**: `@CreatedDate`, `@LastModifiedDate` 등을 활용하여 데이터의 생성·수정 시각 및 변경 이력을 자동으로 기록하고 관리합니다.
- **Pageable과 결과 타입**: 페이징 처리를 위해 `Pageable` 객체를 파라미터로 넘기며, 전체 카운트 쿼리를 포함하는 `Page<T>`와 다음 페이지 존재 여부만 판단하여 무한 스크롤에 유리한 경량 타입인 `Slice<T>` 중 선택하여 반환받을 수 있습니다.
- **사용자 정의 리포지토리**: 기본 제공 기능으로 구현하기 어려운 복잡한 동적 쿼리나 로직을 `Impl` 접미사를 붙인 커스텀 구현체 클래스로 분리하여 확장성과 유지보수성을 확보합니다.

#### 주제 4: QueryDSL
- **개념 및 장점**: 자바 코드로 JPQL/SQL 쿼리를 작성할 수 있게 해주는 객체지향 쿼리 라이브러리로, 실무에서는 복잡한 조건을 안전하게 조립하는 **동적 쿼리** 구현을 위해 필수로 사용됩니다.
- **Q클래스**: 빌드 시 `@Entity` 클래스를 기반으로 자동 생성되는 메타 모델 클래스로, 내부의 경로 객체(StringPath, NumberPath 등)와 다양한 조건 메서드(`eq()`, `contains()`, `gt()` 등)를 제공합니다. 문자열 기반 JPQL과 달리 오타나 타입 불일치를 **컴파일 단계**에서 바로 잡아주는 강력한 안정성을 가집니다.

### 오늘의 도전 과제와 해결 방법
- 도전 과제 1: 묵시적 조인으로 인한 성능 저하 우려
    - **해결 방법**: 실무 지침에 따라 가독성이 떨어지고 예측하기 힘든 묵시적 조인 대신, JPQL 내에 `join` 문을 직접 선언하는 **명시적 조인**을 사용하여 실행 계획을 명확히 제어하도록 코드를 개선했습니다.
- 도전 과제 2: 연관 엔티티 조회 시 발생하는 N+1 문제
    - **해결 방법**: `fetch join`을 적용하여 필요한 연관 데이터를 한 번의 쿼리로 묶어서 함께 즉시 로딩하도록 처리하였고, 데이터 중복이 발생할 수 있는 경우 `distinct` 키워드를 추가하여 결과를 최적화했습니다.

### 오늘의 회고
- 순수 JPA의 값 타입 설계부터 JPQL의 심화 문법(조인, 페이징), 그리고 이를 편리하게 확장해 주는 Spring Data JPA와 QueryDSL까지의 유기적인 흐름을 정리할 수 있었습니다.
- 특히 실무에서 성능 최적화의 핵심이 되는 N+1 문제의 원인과 해결책(`fetch join`, `@EntityGraph`, `Slice` 활용)을 명확하게 이해하게 되어 유익했습니다. 앞으로 복잡한 동적 쿼리가 필요한 비즈니스 로직에는 컴파일 시점에 에러를 잡을 수 있는 QueryDSL을 적극 도입해 보아야겠습니다.
