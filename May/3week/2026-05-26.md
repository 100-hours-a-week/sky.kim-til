## 1. 주요 개념 한줄 정리

#### 주제 1: 데이터베이스 (Database)

* **정의:** 여러 사람이나 시스템이 공유하여 사용할 목적으로, 체계적으로 통합 및 관리되는 데이터의 집합입니다.
* **한줄 요약:** 여러 사람이나 시스템이 사용할 목적으로 체계적으로 통합 및 관리되는 데이터의 저장소입니다.

#### 주제 2: ERD (Entity Relationship Diagram)

* **정의:** 개체와 관계를 한 눈에 알아볼 수 있도록 그려놓은 도표입니다.
* **한줄 요약:** 개체(Entity)를 저장할 때 개체들의 정보와 개체들의 관계를 한눈에 볼 수 있게 그려놓은 도표입니다.

#### 주제 3: 인덱스 (Index)

* **정의:** 데이터베이스 분야에 있어 테이블에 대한 조회 동작의 속도를 높여주는 자료 구조입니다.
* **한줄 요약:** 데이터의 식별자 역할로 조회 동작의 속도를 높여주는 자료구조입니다.

#### 주제 4: 트리 (Tree)

* **정의:** 노드로 이루어진 자료구조입니다.
* **한줄 요약:** 나뭇가지처럼 뻗어나가는 계층적인 구조를 가진 노드 기반의 자료구조입니다.

#### 주제 5: 해시맵 (Hashmap) 및 해시 (Hash)

* **정의:** 다양한 길이를 가진 데이터를 고정된 길이의 데이터로 매핑한 값입니다.
* **한줄 요약:** 다양한 길이를 가진 데이터를 고정된 길이의 해시값으로 매핑하여 키(Key) 값으로 사용하는 자료구조입니다.

#### 주제 6: 풀 텍스트 인덱스 (Full Text Index)

* **정의:** 전문 검색 또는 풀텍스트 검색은 텍스트 검색에서 컴퓨터에 저장된 문서 또는 전문 데이터베이스를 검색하는 기법입니다.
* **한줄 요약:** 텍스트를 나누고 이를 키값으로 삼아, 문서나 전문 데이터베이스 내에서 본문 검색을 빠르게 수행하는 기법입니다.

#### 주제 7: 트랜잭션 (Transaction)

* **정의:** 데이터베이스 관리 시스템 또는 유사한 시스템에서 상호작용의 단위입니다.
* **한줄 요약:** 데이터베이스 시스템에서 여러 연산을 하나의 논리적 단위로 묶어 처리하는 작업 단위입니다.

## 2. Index 딥다이브

#### 주제 1: Index의 기본 개념과 자료구조

* **개념:** 테이블에 대한 조회(SELECT) 동작의 속도를 획기적으로 높여주는 자료구조입니다.
* **트리(Tree) 구조:** 부모-자식 관계를 가지는 노드들로 구성된 계층적 구조이며, 최상위는 '루트 노드', 최하위는 '리프 노드'라고 부릅니다.
* **이진 탐색 트리 (Binary Search Tree):** 값들이 정렬되어 있어 왼쪽 서브트리는 부모보다 작은 값, 오른쪽은 큰 값을 가집니다. 원래는 $O(\log n)$의 탐색 시간을 보장하지만, 순서대로 데이터가 삽입되어 한쪽으로 치우치면 단일 연결 리스트처럼 작동하여 $O(n)$으로 성능이 악화되는 문제점이 있습니다.
* **B-Tree:** 이진 트리와 달리 하나의 노드가 여러 개의 자식을 가질 수 있는 밸런스 트리입니다. 모든 리프 노드가 같은 깊이에 위치하도록 자동으로 균형을 유지하며 대량의 데이터 검색에 효율적입니다. 내부 노드는 '탐색 기준값', 리프 노드는 '실제 데이터 대표값'으로 키의 역할이 분리됩니다.
* **B+Tree:** MySQL InnoDB가 채택한 구조입니다. B-Tree와 달리 **실제 레코드는 최하위 리프 노드에만 저장**되고, 내부 노드에는 경로 결정을 위한 키만 존재합니다. 특히 리프 노드들이 **연결 리스트**로 연결되어 있어 범위 검색(Range Scan) 시 연속적인 이동이 가능해 매우 효율적입니다.

#### 주제 2: 클러스터형 vs 비클러스터형 인덱스

* **클러스터형 인덱스 (Clustered Index):** 데이터가 인덱스 순서대로 **물리적으로 정렬**되어 저장되는 구조입니다. 테이블당 단 하나만 존재할 수 있으며, MySQL InnoDB에서는 기본 키(PK)가 자동으로 이 역할을 수행합니다. (예: 테이블의 `id` 값)
* **비클러스터형 인덱스 (Non-Clustered Index):** 실제 데이터와 물리적으로 분리되어 별도의 인덱스 테이블을 구성하는 인덱스입니다. 인덱스 페이지는 B-Tree/B+Tree 구조를 따르며, 최하위 리프 페이지에는 실제 데이터가 저장된 주소값(포인터)이 들어있습니다. (예: 이름 + 핸드폰 번호 조합 인덱스)
* **인덱스 탐색 경로:** `루트 페이지` (최종 목적지 진입 기준표) $\rightarrow$ `중간 페이지` (리프 페이지 경계를 구분하여 검색 가속화) $\rightarrow$ `리프 페이지` (실제 데이터 주소 보유) 순으로 찾아갑니다.

#### 주제 3: 고효율 인덱스 설계 지표 (Cardinality & Selectivity)

* **카디널리티 (Cardinality):** 특정 컬럼에서 데이터 값의 고유성(Unique)을 나타내는 지표입니다. 중복이 적고 고유한 값이 많을수록 "카디널리티가 높다"고 표현합니다. (예: 주민등록번호는 높음, 성별은 낮음)
* **선택도 (Selectivity):** 다음 수식으로 계산되며, 1에 가까울수록 인덱스로 지정하기 적합합니다. 성별처럼 데이터가 늘어날수록 분모만 커져 0에 수렴하는 컬럼은 인덱스로 부적합합니다.

$$\text{Selectivity} = \frac{\text{Cardinality}}{\text{Total Number of Records}}$$


* **다수 컬럼 인덱스 (Composite Index):** 여러 컬럼을 조합해 인덱스를 만들 때는 반드시 **카디널리티가 높은 컬럼을 앞순서로** 배치해야 검색 성능이 극대화됩니다.

#### 주제 4: 인덱스 사용 시 주의점과 트레이드오프

* **성능 트레이드오프:** 인덱스를 구축하면 조회(SELECT) 속도는 비약적으로 상승하지만, 데이터 삽입/수정/삭제(INSERT, UPDATE, DELETE) 시 인덱스 페이지도 함께 갱신해야 하므로 **쓰기 성능 오버헤드**가 발생합니다. 저장 공간과 관리 비용도 함께 증가합니다.
* **페이지 분할 (Page Split):** InnoDB는 16KB 크기의 '페이지' 단위로 데이터를 관리합니다. 정렬 상태를 유지해야 하는 인덱스 페이지가 꽉 찬 상태에서 '중간 순서'에 새로운 데이터가 삽입되면, 페이지가 강제로 반으로 쪼개지는 '페이지 분할'이 일어납니다. 이 과정에서 디스크 공간 새로 할당, 데이터 이사, 상위 안내판(루트/중간 페이지) 업데이트 작업이 동시다발적으로 일어나 **디스크 I/O가 폭발하며 대량 쓰기 작업 시 심각한 병목을 유발**합니다.
* **운영 시 주의점:** 대량 변경 작업(Bulk Insert 등) 시 인덱스 유지 비용이 크며, 인덱스 재구성 작업(`REINDEX`, `ALTER TABLE` 등)은 서비스 중 락(Lock)을 유발할 수 있어 실시간 서비스에서는 고도의 운영 전략이 필요합니다.

#### 주제 5: 고급 활용 기법 (커버링 인덱스와 EXPLAIN)

* **커버링 인덱스 (Covering Index):** 쿼리 조회에 필요한 모든 컬럼이 인덱스 자체에 다 포함되어 있는 상태를 말합니다. 이 경우 실제 데이터 블록을 쳐다보러 디스크로 가지 않고 **인덱스 페이지 내부에서만 데이터를 바로 반환**하므로 실행 속도가 압도적으로 빠릅니다.
* **커버링 인덱스 실무 예시:**
```sql
-- 1. 테이블 생성 (pk_id는 클러스터드 인덱스)
CREATE TABLE member (
    pk_id INT AUTO_INCREMENT PRIMARY KEY,
    age INT NOT NULL,
    name VARCHAR(50) NOT NULL,
    region VARCHAR(50) NOT NULL,
    phone VARCHAR(50) NOT NULL
);

-- 2. age 컬럼에 보조 인덱스 추가
CREATE INDEX idx_member_age ON member (age);

-- [실패 케이스] 인덱스에 없는 'name'을 찾기 위해 실제 데이터 페이지를 뒤져야 함 (비용 높음)
EXPLAIN SELECT name FROM member WHERE age = 20; 
-- 결과: Index lookup... (cost=0.7)

-- [성공 케이스] 인덱스에 있는 'age'와 PK인 'pk_id'만 조회하므로 데이터 페이지에 접근 안 함 (비용 낮음)
EXPLAIN SELECT pk_id, age FROM member WHERE age = 20; 
-- 결과: Covering index lookup... (cost=0.45)

```


* **EXPLAIN 명령어:** 데이터베이스의 '옵티마이저'가 수립한 최적의 쿼리 수행 경로(실행 계획)를 사람이 읽을 수 있는 표 형태로 출력해 주는 명령어입니다. 느린 쿼리를 튜닝하고 인덱스가 제대로 타는지 확인할 때 사용하는 필수 도구입니다.
